后端总体设计与架构方案

本文供项目负责人和研发团队确定后端建设方向，回答后端负责什么、为什么这样拆分、数据如何组织、业务如何流转，以及怎样从本机版本推进到可运营的线上系统。本文是架构设计方案，不是联调或测试报告。

一条贯穿产品的业务主线

用户从生命、身体、心智三个入口表达当下需要，进入可信内容和可执行练习，留下自己的记录，再获得适合的学习或老师服务。后端要保存这条关系链：用户需要 → 内容与实践 → 个人记录 → 回望与下一步。

三大地图是同一用户体系下的三种业务视角，不拆成三个独立后端。课程、老师和AI可以服务多个地图，个人记录则始终属于具体用户。东方智慧的后端也不是医疗诊断引擎或命运结论引擎。

总体选择

采用模块化单体作为下一阶段主架构。沿用现有Python服务基础，先在一个部署单元内建立清晰的身份、内容、成长记录、社群、服务和集成边界。当前规模没有拆成微服务的必要；先保证业务归属、事务、权限和可维护性，后续按真实压力拆分。

设计原则具体落点
用户为中心账号作为业务主键；三个地图、学习与服务关联到同一用户，不在前端拼出互不相通的档案
内容可信来源、授权、审核和发布范围分开管理；能否公开不等于能否给AI引用
状态可信未接入显示未接入；本机保存不冒充服务器保存；套餐展示不等于会员已生效
运营可用后台通过API操作业务，不直接改数据库；发布、审核、版本和导出可追溯
演进可控先补数据归属和业务分层，再接真实外部服务，最后完成生产部署

现状与目标的阅读方式

“现状”描述当前真实文件和能力；“目标设计”描述后续应建设的结构。现有后台界面不是整个后端，管理端只是后端的一种使用入口。本方案不把尚未实现的分层、支付、云同步或上线能力写成既成事实。

一次业务请求如何经过后端

以提交老师需求为例：路由识别请求 → 认证获得当前用户 → 校验老师是否已发布、日期和正文 → 服务模块创建待处理需求 → 在同一事务中写业务数据与必要审计 → 提交事务 → 返回需求编号与状态。用户不能自行传owner决定归属，运营也不通过直接改表处理需求。

模块之间怎样协作

课程模块提供内容及访问要求，权益模块回答用户是否能读；老师服务模块引用已发布老师资料，身份模块提供当前学员；成长记录模块引用内容编号记录实际行为；AI只能通过受控的上下文接口获取用户明确允许的资料，不能任意查询整库。

为什么不按页面建后端

“首页”“智慧馆”“我的”是展示组合，不是独立业务主体。同一课程可出现在智慧馆、心智地图和收藏中，后端仍只有一个课程身份与发布状态；同一条个人记录可供个人档案和趋势回看引用，但不能复制成多份相互矛盾的数据。

需要补齐的数据结构

内容授权：目标增加内容来源、授权主体、可公开范围、使用期限、是否允许收费与AI引用。三大地图标签与内容传统/授权范围是两个维度，不能因为都叫“东方文化”就混用权限。

学习与成长：目标把练习会话、学习进度和收藏等浏览器记录纳入账号级模型；保留内容版本或必要快照，保证内容更新后历史行为仍能解释。

订单与权益：目标增加订单、支付事件、订阅或权益授予记录。套餐内容只定义价格和说明；用户是否拥有权益由真实业务记录决定。

数据库变更规则

当前初始化建表不等于正式迁移机制。目标建立迁移编号、升级脚本、备份与回滚说明，新增索引对应明确查询场景。跨多张表的业务写入使用事务，不能出现业务成功但关键状态只保存一半。

东方智慧 后端总体设计　/　05

个人数据与成长档案设计

账号归属是第一条边界

当前服务器记录按账号或访客Cookie归属，浏览器仍有本地档案、收藏和偏好。目标是将“账号级业务数据”“设备级偏好”“临时离线草稿”分开：换账号不串档，换设备不丢服务器已有数据，离线草稿不能自动归给错误账号。

目标写入流程

用户操作 → 生成客户端操作编号 → 本地显示待同步状态 → 服务端认证并校验 → 按幂等规则落库 → 返回服务端编号、版本与更新时间 → 客户端确认已同步。离线时进入待发送队列；重连或重新登录后只重传当前账号的操作。该队列与完整读回接口尚待建设。

不同记录采用不同冲突策略

数据类型目标策略原因
签到与每日抽卡同账号同日期幂等，保留首次服务端成功结果防止重试生成两次签到或改变当日抽卡
身体与情绪自述明确当前版本，冲突时保留双方信息或提示选择不能静默覆盖另一个设备上的更新
练习及音乐会话按会话或操作编号追加，服务端去重多个真实练习不应被同日唯一键合并
收藏按用户和内容编号唯一，增删操作可重放多次点击和离线重试应得到一致集合
外观与音量默认设备偏好，可选账号偏好同步设备体验设置与个人业务事实分开

档案如何产生

成长档案由真实记录聚合生成，视图可按生命、身体、心智和日期筛选。聚合值要能追溯原始来源，不用演示分数代替真实结论。自述、练习时长、设备测量和AI辅助总结分别标注来源，不合并成未经验证的健康诊断。

访客转登录

目标由用户明确选择是否将该设备的访客记录归入当前账号，校验冲突并记录迁移结果；不静默把共享设备上所有历史记录并入新登录人。上线多账号和跨设备使用前，应先完成这一部分。

核心业务流程与状态设计

业务状态与流程服务端必须把守的规则
内容配置草稿 → 发布 → 归档；修改生成版本，可恢复发布与排序只有服务端能确定；归档不从内置默认内容复活
社群内容草稿 → 待审核 → 公开或驳回；公开后可下架作者不能直接审批自己；修改公开正文需重新审核；驳回/下架留原因
老师需求待处理 → 已受理 → 已结束；符合条件时取消学员只看自己；老师资料须公开；后续需严格限定状态迁移和排班冲突
设备授权未连接 → 已同意待接入 → 收到真实数据；可解除测量必须关联有效授权；撤权后拒绝推送；按连接 指标 时间去重
会员业务当前为配置和本地流程预览；目标为待支付 → 支付确认 → 权益生效 → 到期或退款回调验签与订单幂等；客户端成功页不能授予权益

全局计时单独建账

进入APP自动心跳，不提供用户暂停累计；按账号约束一个活动段，多窗口不重复计算。超过心跳有效区间后结算旧段，重新进入再开新段；跨天按时区拆分。练习播放器的暂停和全局APP使用时长是两套语义，不能共用一份“正在运行”开关。

状态不只写在界面上

上表是目标工作流规则。现有实现已使用这些状态值，但部分取消和受理接口仍需进一步收紧允许的前置状态。应由业务服务统一判断，例如已结束需求不能再次受理；不能仅靠隐藏按钮防止非法迁移。

事务与副作用

业务状态及关键审计在同一事务内提交。发送通知、长时AI任务、转码等外部副作用不要长时间占住数据库事务；出现实际异步需求时再引入任务队列与可靠事件记录。支付回调需可安全重放，设备推送需可去重。

接口权限与外部服务设计

接口分为三条通道

通道身份与权限主要边界
用户业务API登录会话或明确访客上下文只访问本人记录、双方好友业务和已公开内容
运营管理API管理角色及对象级授权内容发布、审核、服务处理、角色与凭据配置分开授权
供应商回调API供应商凭据或签名不把用户Cookie当作设备或支付服务身份

统一接入层

目标统一请求校验、错误代码、请求编号、时间格式、分页和幂等约定。当前接口已使用JSON和明确HTTP状态，但错误仍主要依赖中文error文本，部分时间字段命名也不统一。演进时先兼容旧响应，再给前端明确迁移期，不一次性破坏已有客户端。

AI如何接入

用户问题先经过身份与上下文授权，再传给AI适配层。系统提示词、内容授权范围、模型和凭据由服务端管理；只有允许被AI引用的资料才进入检索上下文。后续应保留来源依据、失败状态与必要审计，处理超时、限额和取消。AI是学习和觉察助伴，不替代老师或医疗判断。

设备如何接入

用户同意 → 创建账号专属连接 → 供应商完成真实授权 → 服务端接收带时区和来源的测量 → 指标映射与校验 → 持久化 → 按本人权限返回。每个供应商独立适配；缺少SDK或OAuth资料时，不能把本地接收接口当成硬件已接通。

媒体与权益

当前媒体位于SQLite并按公开状态、作者和管理权限读取。生产目标为对象存储中的不可猜测对象引用，由业务API校验后提供短期授权访问；课程付费权益必须由服务端决定，不能在前端藏一个按钮就算保护完成。

隐私访问

管理统计、审核公开内容和读取个人自述是不同权限。常规运营优先使用元数据和统计；私信和个人自述不出现在普通管理导出中。未来如需客服访问敏感内容，应有明确目的、授权范围、期限和审计。

数据库和媒体如何选择

先以真实数据量、并发写入和备份恢复目标决定数据库演进。SQLite继续承担本机开发与验证；当需要多实例应用、更多并发写入或更成熟的运维能力时，再迁移到服务型关系数据库。迁移前建立数据库访问边界，避免业务逻辑依赖到处散落的SQLite细节。

媒体体量会比文字记录增长更快，生产阶段优先把大媒体从业务库拆到对象存储，数据库保留素材编号、所有者、类型、大小、引用和审核状态。不要一开始就为尚不存在的流量引入一整套分布式系统。

上线必须具备的运行能力

独立环境配置与服务端密钥管理；HTTPS与生产Cookie；首次管理员安全初始化；数据库迁移；错误和访问日志；备份及恢复演练；媒体与接口限额；健康检查与告警。增加请求编号后，前台错误能够关联到服务端日志，但日志不记录密码、令牌或敏感正文。

什么时候才拆服务

只有出现独立伸缩、故障隔离或团队边界需求时，才考虑拆媒体处理、通知、AI长任务等模块。核心身份、内容权限与权益保持统一契约；不是因为页面多或功能多，就直接拆成大量微服务。

实施顺序与交付规划

按业务风险与依赖排序推进，不先花时间替换框架名称。每阶段交付可用的业务切片，并明确当前完成和后续设计的边界。

阶段具体实施退出条件
第一阶段 数据归属账号级本地隔离；访客迁移；个人记录读回；待同步队列；操作幂等与冲突策略换账号不串档；重连不重复写入；跨设备恢复范围清楚
第二阶段 后端分层按业务域迁出路由逻辑；封装持久化与事务；建立迁移版本；统一错误和时间约定原接口兼容；模块职责清晰；升级与恢复可重现
第三阶段 可信内容与服务来源与授权；老师服务状态校验；内容分页检索；素材所有权和访问边界运营能管理真实内容；授权和发布范围不混淆；服务流程不靠手工改表
第四阶段 外部集成真实AI与设备；正式支付和权益；超时 重试 回调去重；外部授权撤销真实资料逐项验收；服务端判定权限和成功状态

用户与角色、内容配置、社群发布审核、好友消息、老师需求、五类观察记录、计时账本、设备接收、AI适配、版本审计和本机管理台已经具备基础。后续应围绕上述真实基础渐进改造，而不是再做一套只展示菜单的后台。

需要负责人确定与提供

先确定多账号与跨设备档案的目标范围、哪些内容可被AI引用、老师服务如何受理、付费会员具体权益和退款规则；再提供内容授权、真实老师资料、供应商SDK、AI权限、支付主体及部署环境。技术模块必须服从这些业务边界，不能替业务方臆造。
